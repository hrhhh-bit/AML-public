## HARD CONSTRAINTS (axioms)
1. ZERO micro-numerical noise: NEVER output wallet addresses (0x... / bc1...
   / T...), exact amounts, gas fees, timestamps, tx hashes or token symbols.
2. PURE topological abstraction: abstract roles, chains, DAG levels and
   operations only. Chain labels MUST be abstract: Chain_A, Chain_B, ...
3. Node roles MUST be: Source, Intermediate, Asset_Conversion, Cross_Chain,
   Aggregator, Target.
4. Edge operations MUST be: Transfer, Swap, Bridge, Split, Merge.
5. Node `level` MUST strictly increase along every edge (DAG topological
   order, sources at level 0).
6. `pattern_type` MUST be one of: Peeling_Chain, Chain_Hopping,
   Multi_Layering_Split, Token_Obfuscation, Integration_Merge.
7. FLOW ARCHETYPE normalisation: `flow_share` is ALWAYS the local OUT-degree
   distribution ratio of its SOURCE node; for EVERY node the out-edge shares
   must sum to exactly 1.0 (tolerance 0.01). Single out-edges MUST carry
   1.0; Split out-edges must sum to 1.0. NEVER write a downstream merge
   target's IN-FLOW weight onto an upstream edge.
8. CROSS-CHAIN ledger law: any edge whose source and target live on
   DIFFERENT chains MUST use the Bridge operation. Transfer / Swap / Split /
   Merge can never cross chains.
9. ASSET_CONVERSION contract: an Asset_Conversion node must carry exactly one
   adjacent Swap edge (never Transfer on BOTH sides).
10. Every motif MUST carry meaningful `preconditions` (min_level,
    allowed_node_roles, required_chains, max_active_branches) and a
    `post_state_effect` (branch_increment, chain_transition, target_chain,
    next_recommended_roles).

## ENTITY GROUNDING INVARIANT (grounded_chains)
- Output a top-level `grounded_chains` list naming ONLY the abstract chain
  labels actually evidenced in the report.
- Every `chain` value used by ANY node in BOTH phases MUST appear in
  `grounded_chains`. The number of distinct chain labels used by the motifs
  must NEVER exceed the number of chains declared in `grounded_chains`.
- NEVER invent an intermediate relay chain or ghost node just to make the
  graph look bigger. A direct consolidation (funds merge straight into an
  aggregator) is correct; a fake "CC_A -> CC_B" relay is hallucination.

## TWO-PHASE CONTRACT
- `phase_a_inflow_motifs`: Fan-in / consolidation / first-hop / cross-chain
  ENTRY motifs (funds flowing INTO the laundering structure).
- `phase_b_outflow_motifs`: Fan-out / dispersal / DEX swap / OTC cash-out /
  EXIT motifs (funds leaving the structure toward sinks).
- Put every extracted motif in exactly one phase; leave an empty array []
  when a phase has no motifs.

## MACRO CAMPAIGN TOPOLOGY MANDATE
- MINIMUM EDGE COUNT: each motif MUST have at least 3 edges
  (len(edges) >= 3). Isolated 1-edge transfers or 2-edge simple hops are
  STRICTLY FORBIDDEN.
- CAUSAL FIDELITY: extract each actually-evidenced laundering stage as one
  motif that closes its causal loop (entry -> transformation -> exit).
  Never inflate hop counts, never insert ghost relay nodes or chains, and
  never split one logical flow into per-address fragments.
- CRITICAL: Do NOT mention concrete token symbols (e.g., USDT, ETH, BTC)
  even in descriptions or tags. Always use generic terms like
  'native_asset', 'stablecoin', or 'token'.

## BEHAVIOURAL NORMALISATION
IGNORE marketing prose, tooling ads, white-hat refund narratives and
post-mortem digressions. Extract ONLY the core fund-flow topology actually
described and normalise it to the standard operators:

- "assets moved across blockchains via a bridge"           -> Bridge edge
  (pattern_type: Chain_Hopping, phase_a inflow entry).
- "funds fanned out / many addresses drained it"           -> Split edges
  (pattern_type: Multi_Layering_Split, phase_b outflow).
- "funds consolidated into one recovery / aggregator addr" -> Merge edges
  (pattern_type: Integration_Merge, phase_a inflow).
- "several tokens swapped into one token via a DEX"        -> Swap edge
  (pattern_type: Token_Obfuscation, phase_b outflow).
- "linear chain of small rapid hops, peeling a fraction"   -> Transfer edges
  (pattern_type: Peeling_Chain, phase_b outflow).
- "sold via OTC / P2P desk, cashed out to fiat"            -> Transfer into
  the OTC acceptor address (pattern_type: Integration_Merge, phase_b).

### REPORT SEGMENT ###
Incident Summary
On 6 September 2026, the Liquid Network was exploited through a vulnerability in the Elements codebase used to validate Confidential Transactions. The issue stemmed from an ambiguous cache-key encoding in the rangeproof verification cache, allowing two different validation inputs to produce the same cached entry. The attacker first crafted setup transactions and primed the cache, then submitted a malicious inflation transaction that reused the cached validation result and created unauthorized L-BTC. Approximately 3,998.5 L-BTC, valued at $318.7 million at the time of the exploit, was affected, with the attacker subsequently pegging out the assets into native Bitcoin.
Background
Liquid is a Bitcoin sidechain built on Elements. BTC locked in the Liquid Federation’s Bitcoin wallet backs L-BTC issued on the sidechain. Under the intended peg model, one L-BTC represents one BTC held by the federation.
Elements supports “Confidential Transactions” and “Confidential Assets”. Instead of publishing an amount directly, an output can contain a Pedersen value commitment. An asset may also be represented by a commitment. The transaction’s commitment equation establishes that inputs and outputs balance algebraically, while a ‘rangeproof’ demonstrates that each hidden output value lies in an allowed nonnegative range.
In particular, rangeproof validation is part of ensuring that a confidential amount is both legitimate and cannot be abused to create value outside the permitted range. Actual validity also depends on: rangeproof + value commitment + asset commitment + scriptPubKey. https://github.com/ElementsProject/elements/blob/elements-23.4.0rc3/src/script/sigcache.cpp?utm_source=chatgpt.com
The script is supplied to secp256k1_rangeproof_verify as additional committed data. A proof valid for one (C, X, S) tuple is not automatically valid for a different tuple.
This distinction is essential. Pedersen commitments operate algebraically and can balance a very large positive output against a negative value. The rangeproof is what prevents that negative value from being accepted as a legitimate output. Bypassing the rangeproof check therefore turns an otherwise balanced commitment equation into an inflation mechanism.

2. Prime the live mempool cache
Block connection uses cache semantics that consume an existing entry and do not store a new one on a miss. As a result, connecting block 4,050,335 should remove the cache entry produced when the two visible setup transactions were first accepted. The inflation transaction in block 4,050,336 therefore requires a fresh valid transaction containing the same (P0, C0, X, S0) tuple to reach each accepting node after block 4,050,335 was connected and before the invalid output was checked.
That live primer txid and raw bytes remain unknown; identifying it may require a functionary debug.log, a contemporaneous mempool.dat, a peer-relay capture, or an archived mempool snapshot.

Vulnerability
Elements caches successful rangeproof verifications to avoid repeating an expensive cryptographic operation. Two key constructions are relevant.
Earlier code derived the cache entry from only: That design omitted the asset generator and script even though both affect proof validity. Commit c26d719 attempted to bind the cache entry to the full verification context. It changed the input to: However, the implementation fed the raw fields into one SHA-256 stream without encoding their lengths. Both P and S are variable-length fields. Consequently, distinct tuples can produce the same byte stream by moving bytes across field boundaries. Patched cache implementation. Valid primer: (P0, C0, X, 6a43 || C1 || X || 6a)
Invalid attack: (P0 || C0 || X || 6a43, C1, X, 6a)
The observed setup and attack outputs do not collide under the earlier P || C key. Their old-key inputs differ in both length and content. The construction specifically matches the four-field, undelimited key introduced by the patch. Acceptance therefore points to a c26d719-like implementation combined with a primed cache, although the exact binaries deployed on individual functionaries have not been published.
